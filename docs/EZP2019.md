# EZP2019 / EZP2010 / EZP2023 Programmer Notes

This document captures observed behaviour, protocol quirks, and firmware limitations of the EZP family of SPI programmers (based on the CH552G microcontroller) as encountered while developing the `ezp2019_spi` backend for Scriba.

## 1. Device Identification

| PID   | Marketing Name   | Notes                     |
|-------|------------------|---------------------------|
| 0x310b | EZP2019         | Original device           |
| 0x310c | EZP2019 Plus    | Faster clock variant      |
| 0x310d | EZP2023         | Newer housing / firmware  |

All three expose the same vendor bulk protocol on endpoints:

- `0x01` – bulk OUT (data)
- `0x02` – bulk OUT (commands)
- `0x82` – bulk IN  (responses / data)

VID is always `0x1fc8`.

## 2. Protocol Packet Format (0x40 bytes)

```
Offset 0   : 0x01 for most commands (magic / direction)
Offset 1   : Command ID
Offset 2-3 : Protocol selector (0 = SPI)
Offset 4-5 : Page size (LE)
Offset 6-7 : Timeout / retry count (LE)
Offset 8-11: Transfer length (BE)
Offset 12-15: Chip ID (24-bit JEDEC in big-endian)
Offset 16-31: reserved / padding
```

Responses reuse the same 0x40-byte structure. The first byte of a CONNECT reply (`result[0]`) is `0x00` or `0x01` on success; later bytes contain the 24-bit ID in positions 1-3.

## 3. Command IDs

| Name            | Value | Purpose                              |
|-----------------|-------|--------------------------------------|
| EZP_CMD_CONNECT | 0x09  | Probe / configure chip               |
| EZP_CMD_READ_SPI| 0x07  | Prepare read stream                  |
| EZP_CMD_STATUS  | 0x0A  | Poll busy / ready bit                |
| EZP_CMD_TRIGGER | 0x05  | Start address for read/write         |
| EZP_CMD_ERASE   | 0x02  | Full-chip erase                      |
| EZP_CMD_RESET   | 0x08  | Soft reset of the programmer         |

## 4. Critical Firmware Behaviours

### 4.1 Cached Chip ID (The Core Limitation)

After a successful `CONNECT` the CH552G firmware stores the detected 24-bit JEDEC ID in internal RAM. Subsequent `CONNECT` commands — even after a full USB bus reset or `EZP_CMD_RESET` — return the **same cached ID** even when the SPI flash has been physically removed.

- `result[1..3]` always contain the last seen ID.
- ID `0x000000` is **never** returned by the stock firmware once a chip has been detected at least once.
- There is no "chip present" flag, no "last operation error" byte, and no timeout that would indicate an electrically absent device.

Consequently the host driver **cannot** implement reliable "chip removed" detection using only the vendor protocol.

### 4.2 USB Reset Behaviour

`libusb_reset_device()` followed by re-enumeration and re-claim is performed on every `ezp_do_connect()`. This clears any stalled bulk endpoints but does **not** clear the cached ID described above.

### 4.3 STATUS Polling

`EZP_CMD_STATUS` returns a single status byte. Bit 0 == 0 means "ready". The firmware will keep reporting busy (bit 0 == 1) for a missing chip on some operations, but the `CONNECT` path itself never reflects absence.

### 4.4 Data Read of Absent Chip

When a `READ` (opcode 0x03) or `FAST_READ` is attempted on a missing chip the programmer either:

- returns 0xFF bytes (sometimes), or
- hangs until the bulk IN transfer times out.

The current driver therefore uses a 1-byte data read probe after `CONNECT` in an attempt to verify presence, but this probe itself can loop or hang because the firmware still believes a chip is attached.

## 5. Work-arounds Implemented in Scriba

1. `ezp_chip_id == 0` after `CONNECT` is treated as "no chip".
2. A USB reset + `EZP_CMD_RESET` is issued before every `CONNECT`.
3. `ezp_chip_configured` is cleared on shutdown so the next invocation starts fresh.
4. Debug builds emit the full 6-byte `CONNECT` response for diagnostics.

These measures are the best that can be achieved without replacing the CH552G firmware.

## 6. Recommendations for Future Firmware

A corrected firmware should:

- Re-scan the SPI bus (assert CS, clock out 0x9F, read three bytes) on every `CONNECT` or `RESET`.
- Return ID `0x000000` and set `result[0] = 0xFF` when no chip responds.
- Provide a distinct "chip absent" status code rather than reusing the previous ID.
- Expose the raw SPI pins via a vendor control request so a host driver can perform its own presence test if desired.
